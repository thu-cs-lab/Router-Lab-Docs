## L4S：DualPI2 / iDualPI2 { #l4s }

### 背景与动机

网络拥塞时，交换机出口的排队会增加端到端时延。较大的缓存可以容纳更多突发流量，但也可能使数据包长时间等待。若仅在缓存满时丢包，端系统收到拥塞信号时，队列可能已经很长。主动队列管理（Active Queue Management，AQM）尝试在队列完全填满之前进行标记或丢包，让端系统更早调整发送速率。

L4S 是 Low Latency, Low Loss, Scalable Throughput 的缩写。它通过网络侧的拥塞标记与端系统的可扩展拥塞控制配合，追求低排队时延、低丢包和较高吞吐。L4S 不只是交换机上的一个算法，还涉及 ECN 协议、网络队列管理和发送端响应。[RFC 9330](https://www.rfc-editor.org/rfc/rfc9330.html) 给出了整体架构。

当 L4S 流量与传统拥塞控制流量共享瓶颈时，还需要考虑两者能否合理共存。双队列耦合 AQM 将两类流量分开排队，同时关联两类队列的拥塞反馈，避免只降低一类流量时延、却忽略另一类流量获得的服务。

### 项目内容

项目仓库：[p4lab2025-grp01](https://git.tsinghua.edu.cn/network-2025fall/p4lab2025-grp01)。

项目实现包含三套交换机程序与一套测试工具：

| 目录 | 内容 |
|---|---|
| `p4_vanilla/` | 普通转发基线 |
| `p4_DualPI2_3.0/` | 在出口流水线执行概率标记、丢包的 DualPI2 版本 |
| `p4_iDualPI2/` | 将 Classic 流量的主要丢包决策前移到入口流水线的 iDualPI2 版本 |
| `run_test/` | iperf3 多流负载、TCP 指标采集和绘图工具 |
| `report/` | 实验说明与两种实现的结果图 |

项目围绕以下三部分展开：

1. 在交换机中区分 L4S 与 Classic 流量，配置相应队列和调度参数。
2. 根据队列时延更新拥塞概率，控制数据面的 ECN 标记与丢包行为。
3. 搭建包含 Cubic 与 Prague 流量的测试环境，记录时延、发送状态与吞吐变化。

### 实现方式

**数据面处理每个包，控制面计算和更新概率。** 数据面记录出口队列时延，通过寄存器向控制面提供样本；控制面中的 `pi_worker()` 周期性读取样本，更新 PI 状态，再将用于 mark/drop 的概率写回数据面。数据面通过随机数与概率阈值比较，决定是否标记或丢弃当前数据包。

这种划分把较复杂的概率计算留在控制面，将逐包操作转化为查表、读写寄存器、随机数比较和包头修改。控制面直接计算用于两类流量的概率，减少数据面的计算需求。

在 DualPI2 版本中，入口根据 ECN 相关位选择队列，出口执行主要 AQM 逻辑：L4S 流量按条件设置 CE，Classic 流量按条件丢包。实现使用不同队列 ID，并由控制面配置 Traffic Manager 的队列调度和端口限速。

在 iDualPI2 版本中，主要的 Classic 丢包判断前移到入口，使被选中的包在进入出口队列前丢弃。

协议方面，ECT(1) 用于识别 L4S 流量，CE 表示已出现拥塞；ECT(0) 和 Not-ECT 的处理方式与之不同。相关定义见 [RFC 9331](https://www.rfc-editor.org/rfc/rfc9331.html)，双队列耦合机制见 [RFC 9332](https://www.rfc-editor.org/rfc/rfc9332.html)。项目代码采用了简化的按位分类和标记逻辑，记录的是该原型的行为，不等同于完整协议兼容性验证。

## 交换机内机器学习流量分类 { #traffic-classification }

### 背景与动机

网络流量分类可以为设备识别、策略选择和流量分析提供依据。传统方式通常把流量或统计数据发送到主机处理；可编程交换机则提供了另一种可能：在数据包经过流水线时提取特征，直接完成轻量推理。

交换机不能直接运行通用机器学习框架。复杂算术、循环、大规模状态和流水段依赖都受到约束，因此核心问题是：**如何把已经训练好的模型，转换为有限次匹配、查表和整数运算？**

第二组主要参考 *Do Switches Dream of Machine Learning? Toward In-Network Classification* 及其 IIsy 框架，将模型映射的思路移植到 Tofino。原 IIsy 的公开实现面向 BMv2 和 NetFPGA，项目汇报说明，Tofino 部分需要针对目标流水线重新组织代码，并非直接换一个编译目标即可运行。

### 项目内容与数据集

项目仓库：[p4lab2025-grp02](https://git.tsinghua.edu.cn/network-2025fall/p4lab2025-grp02)。

项目完成了四种传统机器学习模型的数据面和控制面实现：决策树、K-means、朴素贝叶斯、线性 SVM。模型在主机侧离线训练，控制面负责转换参数并下发表项，交换机在包粒度执行推理，不在数据面训练模型。

数据来源为 UNSW-IoTraffic 的原始 pcap。项目先提取特征、按设备信息标注类别，再划分训练集和测试集，训练模型并生成供控制面读取的模型文件。训练与测试按约 8:2 划分。

项目经历了数据清洗与特征压缩：初始特征同时包含 IPv4、IPv6 和独立的 TCP/UDP 字段，之后筛选为 IPv4 数据，合并 TCP/UDP 源端口与目的端口特征，并按硬件资源缩减部分任务的类别数。

最终任务规模如下：

| 模型 | 特征 | 分类或聚类目标 |
|---|---|---|
| 决策树 | 包长、IPv4 协议号、EtherType、源端口、目的端口，共 5 个特征 | Smart-static、Sensor、Audio、Video、Others，共 5 类 |
| K-means | 包长、源端口、目的端口，共 3 个特征 | 3 个簇；分析其与 Smart-static、Video、Others 三类的对应关系 |
| 朴素贝叶斯 | 包长、源端口、目的端口，共 3 个特征 | Smart-static、Video、Others，共 3 类 |
| SVM | 包长、源端口、目的端口，共 3 个特征 | Smart-static、Video、Others，共 3 类，以 3 个超平面进行两两分类 |

### 模型如何映射到数据面

#### 决策树

控制面收集模型中的特征阈值，把原始特征空间划分成区间，为区间分配紧凑索引。数据面先通过各特征的 `range` 表得到区间索引，再根据索引组合匹配决策规则，得到分类对应的出口。

这一设计保留了决策树按阈值划分特征的逻辑，同时压缩了最终决策表的匹配键位宽。代码主要位于 `switch/decision_tree.p4` 与 `ctrl/decision_tree.c`，模型转换脚本位于 `tools/`。

#### K-means

K-means 将包特征视为空间中的点，通过比较到各簇中心的距离确定归属。项目比较距离平方，省去开方；对固定中心和有限取值域，控制面预先计算每个特征的距离平方贡献，数据面查表取得贡献并累加。

最小距离选择需要比较运行时变量。项目针对当时编译器和流水线约束，将相关操作改写为减法、符号位提取及小表选择，并限制数值范围以避免回绕破坏比较结果。特征数与簇数最终缩减为 3，以满足流水段资源要求。

#### 朴素贝叶斯

项目采用高斯朴素贝叶斯，将概率计算转换为负对数代价累加。控制面根据均值与方差，对每个离散特征值预计算各类别的整数代价；数据面查表累加，并选择总代价较小的类别。

这种方法避免在逐包路径中计算概率密度、对数和乘法，但增加了表项需求。项目使用整数缩放、饱和加法和逐级比较，并最终采用 3 特征、3 分类的配置。实现位于 `bayes/`。

#### SVM

项目使用线性 SVM 的 One-vs-One 方式：三个类别之间两两建立超平面，共三个。控制面预计算每个特征值对各超平面得分的贡献，并处理整数缩放与偏置；数据面查表累加得分，提取符号位，再用一个投票表确定类别和出口。

这一流程把乘法移到控制面，并用符号位组合代替复杂的运行时决策。最终提交的是 3 特征、3 分类版本，代码位于 `svm/`。汇报中提到的更大规模配置并未作为完成结果提交。

## OSPF 路由器 { #ospf }

### 背景与动机

静态转发表可以在固定拓扑中完成转发，但无法自动适应网络变化。动态路由协议负责发现邻接关系、交换拓扑信息并计算路由；数据面则根据计算结果转发普通业务包。

这一项目把软件路由器中的 OSPFv3 控制逻辑与 Tofino 硬件转发结合起来，研究的核心是控制面与数据面的职责划分：协议包和异常情况交由控制面处理，已具备路由及下一跳信息的普通 IPv6 包由数据面处理。

它还涉及两种不同的状态：路由表决定目的前缀对应的下一跳与出口，邻居信息提供下一跳 IPv6 地址对应的 MAC 地址。路由已经算出，并不意味着下一跳的链路层地址已经获知；两者需要协同维护。

### 项目内容

项目仓库：[p4lab2025-grp04](https://git.tsinghua.edu.cn/network-2025fall/p4lab2025-grp04)。

| 部分 | 代码位置与内容 |
|---|---|
| P4 数据面 | `switch/`：Ethernet / IPv6 解析、IPv6 最长前缀匹配、下一跳 MAC 查询、包头修改及 CPU upload |
| OSPF 控制逻辑 | `ctrl/main.cpp`、`ctrl/protocol-ospf/`：邻居状态、协议报文、链路状态信息和路由计算 |
| 硬件抽象与同步 | `ctrl/HAL/`：初始化交换机、CPU 收发通道、邻居发现以及 BF-RT 表项操作 |
| 辅助模块 | `ctrl/lookup/`、`ctrl/eui64/`、`ctrl/internet-checksum/`：软件查表、地址生成与校验和 |

### 数据面与控制面的配合

数据面使用 `get_meta` 等表维护接口信息，通过 `ipv6_lpm` 查询目的前缀，取得出口、下一跳和直连标志。直连目的地直接以目的 IPv6 地址进行邻居查询；非直连目的地使用路由给出的下一跳地址。

`change_dst_mac` 负责将下一跳地址映射为目的 MAC。正常转发时，数据面处理 Hop Limit，出口侧设置相应接口的源 MAC；需要本机处理的包，以及下一跳 MAC 尚未查到的情况，通过自定义 upload header 携带接口、目标地址等信息送往控制面。

控制面运行 OSPFv3 的邻居及链路状态逻辑，计算路由结果。硬件抽象层的 `update_routing_table()` 将路由写入硬件 LPM 表，邻居发现相关逻辑将解析出的下一跳 MAC 写入对应表项。两类表项分开维护，分别服务于前缀选路与二层封装。

这一实现的普通转发路径与“把所有包送到 CPU 再查软件路由表”不同：路由和邻居状态具备后，普通业务包可以直接走硬件数据面。源码中的 CPU upload 与软件收发逻辑则承担协议和例外路径。

## 负载均衡：助教介绍的参考方向 { #load-balancing }

### 背景与动机

数据中心网络通常提供多条端到端路径，以获得冗余和更大的总容量。但路径存在并不意味着流量会均匀使用它们：某些路径可能拥塞，另一些路径仍有空余容量。因此，需要设计规则，把流量分配到可用路径上。

2025 年助教选题介绍围绕负载均衡粒度展开，比较了逐流、逐包和逐 flowlet 的方法，并介绍如何通过端口负载、延迟及拥塞信息辅助选路。

### 介绍内容

| 粒度 | 主要思路 | 需要权衡的问题 |
|---|---|---|
| Per-flow（逐流） | 例如 ECMP，根据流标识的哈希选择路径，同一流通常保持路径一致 | 流量大小不同或哈希碰撞时，路径负载可能不均 |
| Per-packet（逐包） | 在包粒度分散流量，可以更细地利用多条路径 | 不同路径时延会引入乱序，端系统对乱序的响应影响实际收益 |
| Per-flowlet（逐流簇） | 根据相邻包的空闲间隔划分 flowlet，在 flowlet 边界重新选择路径 | 时间阈值、路径时延差及状态存储会影响乱序与负载分散效果 |

Flowlet 的基本思路是在同一流的连续突发之间寻找足够长的空闲间隔。交换机保存流或哈希桶的最近到达时间与当前路径；新包到来时判断是否出现新的 flowlet，再决定是否重新选择出口。课件同时介绍了端口带宽、利用率和转发时延等路径质量指标。

助教还介绍了 CAVER：利用 RDMA ACK 携带拥塞信息，通过向量式传播寻找较空闲路径。其动机是仅观察已有流经过的路径，可能遗漏其他低拥塞路径。
